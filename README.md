# ThePScode — 分布式阈值 PS 签名原型

> **一句话**：这是一个**可运行的研究原型 / 课程验证代码**，用 BLS12-381 上的 Pointcheval–Sanders（PS）多消息签名 + Feldman VSS 分布式密钥生成（DKG），演示"两个用户各自持有 3 个节点、门限配置为 2 的密钥集群，由一个协调者代理完成阈值签名与验签"。
>
> ⚠️ **它现在不是生产系统**。第 7 节"离生产级分布式密钥系统的差距"是本文档的重点：当前实现存在**可导致密钥完全泄露的设计缺口**，仅可用于本地演示、算法验证与教学。

## 1. 它实现了什么

### 1.1 业务目标

模拟一个"门限签名服务"：用户不直接持有完整私钥，而是把密钥拆成多份交给多个节点保管；只要凑够门限个数的节点配合，就能代表用户签出一条**用一个统一公钥即可验证**的签名。

- **两个互相独立的用户**：`user_a` 和 `user_b`，各有 3 个节点、门限配置 2。
- **协调者（coordinator）**：客户端唯一入口，负责选节点、发起部分签名、聚合、验签。
- **交叉验证**：用 A 的公钥验证 B 的签名必须失败；篡改消息必须验证失败；未知集群必须被拒绝。

### 1.2 已实现的密码学能力

| 能力 | 实现位置 | 说明 |
|---|---|---|
| PS 多消息签名 Keygen / Sign / Verify | `src/crypto/core.py` | 按论文 Section 4.1/4.2 |
| 签名随机化 Randomize | `src/crypto/core.py` `randomize()` | σ' = σ^t，保持可验证性 |
| (t, n) 阈值 PS 签名 + 部分签名聚合 | `src/crypto/threshold.py` | Lagrange 插值聚合 |
| Feldman VSS 分布式密钥生成 | `src/crypto/threshold.py` + `src/node.py` | 承诺放在 **G2**，与公钥同群 |
| 份额加密落盘与重启恢复 | `src/crypto/storage.py` | scrypt 派生密钥 + AES-GCM |
| 点序列化 / 反序列化（含子群检查） | `src/crypto/utils.py` | 未压缩编码，96B / 192B |
| HTTP 服务（节点 + 协调者） | `src/node.py`、`src/coordinator.py` | Flask |
| 容器编排 | `Dockerfile`、`docker-compose.yml` | 6 节点 + 1 协调者 |

### 1.3 明确**没有**做的事

没有通信加密、没有节点身份体系、没有审计、没有并发/性能优化、没有自动化测试。详见第 7、8 节。

**信任假设（当前代码实际采用，而非文档宣称的）**

- 集群内所有节点是**诚实**的；
- 节点之间、节点与协调者之间的网络是**可信**的；
- 协调者**可信**且不会作恶；
- 没有外部敌手能访问节点 HTTP 端口。

> 这四条假设中任何一条不成立，当前实现都不安全——这是它和生产系统的**根本差别**。

## 4. 密码学方案与关键实现细节

### 4.1 数学背景

- **曲线**：BLS12-381（Type-3 双线性群，G1 ≠ G2，无同态）。
- **私钥**：`sk = (x, y_1, …, y_r) ∈ Z_p^{r+1}`，`r` = 单次签名的消息条数（本项目 `r = 2`）。
- **公钥**：`pk = (g2, X̃ = g2^x, Ỹ_j = g2^{y_j})`。
- **签名**：`σ = (σ₁, σ₂)`，其中 `σ₁ = h ∈ G1` 随机，`σ₂ = h^{x + Σ y_j·m_j}`。
- **验签等式**：`e(σ₁, X̃ · ∏ Ỹ_j^{m_j}) == e(σ₂, g2)`。

### 4.2 已有的正确性处理（值得保留）

这些是代码里踩过坑之后的正确修复，后续升级不要丢：

1. **配对结果必须先做 final exponentiation 再比较**（`core.py:93-97`）。
   `py_ecc` 的 `pairing()` 返回 Miller loop 中间结果，同一个 GT 元素可能有多种非规范表示；直接 `==` 会误判。

2. **Feldman 承诺放在 G2**（`threshold.py:74-80`）。
   PS 的公钥在 G2；若承诺放在 G1，份额验证等式与公钥所在群不一致，验证无法成立。

3. **反序列化做 on-curve + 子群检查**（`utils.py:85-89`、`utils.py:136-140`）。
   防止无效曲线 / 小子群攻击。这是当前代码里少见的、已经带上敌手意识的防御。

4. **哈希加长度前缀 + 拒绝采样**（`utils.py:27-40`）。
   避免长度扩展；拒绝采样避免模偏。

5. **协调者只按第一个 `:` 切分集群定义**（`coordinator.py:56`）。
   修复了 `"user_a:user_a_node1:8000,…"` 被 `split(":")` 切碎的 bug——那会导致节点端口丢失、协调者连到默认 80 端口。

6. **协调者阈值配置"安全失败"**（`coordinator.py:127-129`）。
   未配置阈值时拒绝签名，而不是默认放行。

7. **节点多项式在模块加载时生成一次**（`node.py:50-54`）。
   保证 DKG 重试期间本节点广播的承诺与发出的份额保持一致。

### 4.3 门限参数的语义（容易读错，务必注意）

```python
# node.py:50
_threshold = ThresholdPSSignature(NUM_NODES, THRESHOLD, NUM_MESSAGES)   # (n=3, t=2)
# threshold.py:69-72
def generate_polynomial(self):            # 返回 t+1 = 3 个系数 → 二次多项式
    return [secrets.randbelow(curve_order) for _ in range(self.t + 1)]
# threshold.py:186
if len(partial_sigs) < threshold + 1:     # 至少要 t+1 = 3 个部分签名
    return None
```

- `t = 2` 表示多项式次数为 2，**恢复秘密需要 `t+1 = 3` 个份额**。
- 因此当前配置实际是 **3-of-3**：必须**三个节点全部在线**才能签名。
- `THRESHOLD: "2"` 这个配置名容易让人以为是 2-of-3，读代码时请以 `threshold + 1` 为准。
- 另外 `assert 0 < t < n`（`threshold.py:47`）禁止 `t = n`，配置空间很窄，无法直接表达 3-of-5 这类常见形态。

### 4.4 加密存储

```
文件格式（JSON）: {salt, nonce, ciphertext, cluster, node_id}
密钥派生: scrypt(n=2^14, r=8, p=1, len=32) ← SHARE_PASSPHRASE
加密:     AES-256-GCM(nonce, payload)      payload = {x, y[], global_pk}
```

- 应用层没有 KDF 参数升级机制，`n=2^14` 写死（`storage.py:37`）。
- `global_pk` 一并落盘，使节点重启后无需重跑 DKG（`storage.py:60-61`、`node.py:237-243`）。
- 口令来自环境变量 `SHARE_PASSPHRASE_A/B`，`.env` 里是**测试值**，必须替换。

## 5. 一次完整流程

**阶段一：DKG（节点进程启动后由后台线程触发）**

1. 每个节点等待 peer `/health` 就绪（`node.py:339-360`，最多 60s，每 2s 轮询）。
2. 各节点用**自己模块级的多项式**生成 Feldman 承诺 `C_k = g2^{a_k}`。
3. 每个节点向所有 peer 拉取：
   - `GET /dkg/commitments` → 对方的承诺；
   - `GET /dkg/share_for/<my_id>` → 对方**算好发给我的份额**。
4. 用 `g2^{f(i)} == ∏ C_k^{i^k}` 验证每一份份额（x 以及每个 y）。
5. 验证通过后累加成本节点最终份额 `share = {x, y[]}`。
6. 从各节点承诺的第 0 项求和得到全局公钥：`X̃ = Σ C_{i,0}`，`Ỹ_j = Σ C_{i,j,0}`。
7. 加密落盘（份额 + 公钥）。失败则最多重试 5 次，每次间隔 5s（`node.py:376-382`）。
8. 重启时先尝试 `load_share_from_disk()`，成功则跳过 DKG（`node.py:370-374`）。

**阶段二：阈值签名（`POST /sign`）**

1. 协调者校验 `cluster` 在白名单内、阈值已配置。
2. 协调者生成共享随机点 `h = hash_to_G1(随机 32 字节)`，转成 hex。
3. 依次向集群内**每个**节点发 `POST /partial_sign`（串行，超时 15s）。
4. 每个节点：校验 `cluster` 是否匹配自己 → 反序列化 `h` → 计算
   `σ₂ = h^{x_i + Σ y_{i,j}·m_j}` → 计算 attestation（域分离哈希）→ 返回。
5. 协调者收集 `(party_id, σ₁, σ₂)`；要求**所有** σ₁ 相同。
6. 用 Lagrange 系数在指数上插值，聚合出 `σ₂`，返回 `{sigma1, sigma2, attestations}`。

**阶段三：验签（`POST /verify`）**

1. 协调者从集群**第一个节点**拉取 `/public_key`。
2. 重建 `VerificationKey`，执行配对等式校验（含 final exponentiation）。
3. 返回 `{"valid": true/false}`。

## 6. 如何运行

### 6.1 环境要求

- Python 3.8+（`requirements.txt` 只约束 `py-ecc>=6.0.0`；`Dockerfile` 使用 3.11）。
- 依赖：`py-ecc`、`cryptography`、`flask`、`requests`。
- 代码只使用 `py_ecc.optimized_bls12_381` 这一纯 Python 模块，因此不依赖 `py-ecc` 的 Rust 扩展；
  `Dockerfile` 中安装 Rust 属于保守覆盖。

### 6.2 方式一：Docker Compose（推荐，最接近当前已跑通的形态）

```bash
# 1. 先修改 .env 中的口令与 token，勿使用仓库里的测试值
docker compose up --build
# 2. 另开一个终端
python client/demo.py
```

- 协调者映射到宿主机 `9000` 端口，节点仅在 `ps_net` 内网可达。
- `share_data` 卷保存加密份额。

### 6.3 方式二：宿主机直接运行（7 个进程）

需要 6 个节点进程 + 1 个协调者进程。节点示例：

```bash
NODE_ID=1 CLUSTER_NAME=user_a NUM_NODES=3 THRESHOLD=2 NUM_MESSAGES=2 \
PEER_NODES="http://127.0.0.1:8002,http://127.0.0.1:8003" \
MY_URL="http://127.0.0.1:8001" \
SHARE_PATH="./data/user_a_node1.share" \
SHARE_PASSPHRASE=user-a-passphrase AUTH_TOKEN=vm-test-token-change-me \
PORT=8001 python -m src.node
```

协调者示例：

```bash
CLUSTERS="user_a:127.0.0.1:8001,127.0.0.1:8002,127.0.0.1:8003;user_b:127.0.0.1:8011,127.0.0.1:8012,127.0.0.1:8013" \
THRESHOLD_USER_A=2 THRESHOLD_USER_B=2 \
AUTH_TOKEN=vm-test-token-change-me python -m src.coordinator
```

> `MY_URL` 在当前代码中只作为配置读取（`node.py:38`），节点之间的实际通信地址来自
> `PEER_NODES`，协调者访问节点的地址来自 `CLUSTERS`，因此这三处必须保持一致。

### 6.4 运行注意事项与踩坑记录

- **协调者端口写死为 8000**（`coordinator.py:204`），compose 里通过 `9000:8000` 映射暴露给客户端；
  宿主机直跑时客户端要访问 `http://localhost:8000`。
- **`/verify` 依赖集群第一个节点在线**（`coordinator.py:91`），该节点必须可达。
- **必须让节点以多线程模式运行**：DKG 阶段节点之间会互相发起 HTTP 请求。
  `flask run` 默认 `threaded=True`；若自行改成单线程，DKG 会互相等待而死锁。
- **`messages` 只能是整数列表**：代码里做 `m_j % curve_order`
  （`core.py:65`、`threshold.py:162`），传字符串会在服务端抛异常。
- **`.venv` 不可跨平台复用**：仓库中的 `.venv` 是在 **Linux 虚拟机**内创建的
  （目录结构为 `.venv/bin/python3.12`），在 Windows 宿主机上无法使用，
  需要在目标平台重建虚拟环境并重新安装依赖。
- **必须设置 `SHARE_PASSPHRASE`**，否则 DKG 结果**不会落盘**（`node.py:212`），重启即丢失份额。
- **`requirements.txt` 未固定版本**：安装时可能装到比验证环境更新的 `py-ecc`，
  若出现与 `optimized_bls12_381` 相关的接口/行为差异，建议固定到验证过的版本。

## 7. 离生产级分布式密钥系统的差距（重点）

下面按"距离生产可用的严重程度"排序。**标 P0 的条目意味着：在真实网络中部署，密钥会直接泄露或被伪造。**

### 7.1 P0 — 阻塞上线的安全缺口

#### ① DKG 份额可被任何人无条件索取（密钥直接泄露）

```python
# node.py:278-285
@app.route("/dkg/share_for/<int:target_id>", methods=["GET"])
@require_token
def get_share_for(target_id):
    """返回本节点发给 target_id 的份额 (模块级多项式, 永不变化)"""
    x_share = _threshold.eval_poly(_my_poly_x, target_id)
    y_share = [_threshold.eval_poly(p, target_id) for p in _my_poly_y]
    return jsonify({"x": x_share, "y": y_share})
```

- 这是个**只读 GET**，且对 `target_id` **不做任何所有权校验**：任何能访问该端口的调用方都可以指定任意目标节点索取份额。
- 攻击者只要逐个节点请求 `share_for/1|2|3`，就能拿齐任意节点的全部分量；
  再用 Lagrange 插值即可**重建整体私钥 `x` 与 `y_j`**，此后无需任何节点配合即可伪造签名。
- `AUTH_TOKEN` 是**所有节点共享的同一个静态字符串**（`.env`）；一旦泄露，
  或在**未设置该变量时 `require_token` 直接放行**（`node.py:65`），整个集群的密钥即可被判构。
- 结论：当前实现**没有把份额视为机密**，也**没有把 DKG 做成一次性、可销毁的过程**。

#### ② DKG 无会话绑定、无身份认证、无可验证性

- 没有 DKG 会话 ID / epoch / 参与者集合的承诺，多次运行之间无法区分，也无法防重放。
- 引用的是**裸 GET**，没有消息签名、没有 nonce。
- 没有对"发送方是否真的按 Feldman 承诺发了份额"的**可验证性证明**：
  验证失败只是 `raise ValueError` 后重试（`node.py:199-201`、`376-382`），
  既不能定位作恶节点，也不能提供**可公开验证的问责证据**。
- 没有处理 **equivocation**（同一节点对不同接收者发送不一致的承诺）。
- 结果：**只要有一个恶意/被控节点，就可能让 DKG 走向对攻击者有利的结果，而其余节点毫不知情。**
  生产级 DKG（如 GJKR / Pedersen-DKG / 带投诉阶段的 DKG）必须逐条解决上述问题。

#### ③ 传输完全明文：HTTP + 静态 Token

- 节点之间、节点与协调者之间都是 `http://`，私钥份额、部分签名、全局公钥**全部明文过网**。
- `AUTH_TOKEN` 是共享密钥而非节点身份，无法做**非对称认证**，也无法撤销单个节点。
- 生产系统需要 mTLS 或节点级签名密钥，并对每个请求做**端到端加密 + 完整性保护**。

#### ④ 门限密钥生命周期能力完全缺失

- 没有**密钥刷新（proactive refresh）**：不能定期重随机化份额，无法限制攻击窗口——
  这是门限系统最重要的运维能力之一。
- 没有**重新分享（resharing）**：无法在不更换公钥的前提下增删节点。
- 没有**密钥撤销、失效、版本 / epoch 迁移**。
- 节点重启逻辑（`node.py:370-374`）在份额丢失时会**重新跑 DKG 生成一套新密钥**，
  而其余节点仍持有旧份额——**集群会静默进入"份额不一致"的损坏状态**，
  外在表现只是部分签名验证失败，且没有任何检测与告警。

#### ⑤ 部分签名与聚合缺少完整性校验

- `partial_sign`（`node.py:288-323`）**不校验 `messages` 的长度与类型**：
  `zip(share['y'], messages)`（`threshold.py:161`）在长度不匹配时会**静默截断或忽略多余项**，
  可能产生错误却无法察觉的签名。
- 聚合只检查"所有 σ₁ 相同"（`threshold.py:193-196`），
  **不验证 σ₂ 是否与 σ₁ 满足同一条 PS 关系**，也不校验参与集合是否符合预期。
- 没有拒绝**重复 `party_id`** 的保护：重复条目会污染 Lagrange 集合 `indices`（`threshold.py:189`），
  使插值结果错误，退化为 DoS。

### 7.2 P1 — 协议层缺陷

| # | 问题 | 位置 | 影响 |
|---|---|---|---|
| ① | **门限语义含糊**：`THRESHOLD=2` 实际是 3-of-3（见 4.3） | `node.py:50`、`threshold.py:186` | 容量规划错误，失去容错意义 |
| ② | **配置空间过窄**：`assert 0 < t < n` | `threshold.py:47` | 无法表达 3-of-5 等常见形态 |
| ③ | **协调者单点**：`/verify` 只信任"第一个节点"的公钥 | `coordinator.py:91`、`186` | 该节点作恶或离线即失败 / 被欺骗 |
| ④ | **公钥无共识校验**：各节点各自算全局公钥，从不交叉比对 | `node.py:206-209` | 恶意节点可制造公钥分歧 |
| ⑤ | **`h` 由协调者集中生成并广播**，而非各节点独立贡献随机性 | `coordinator.py:134` | 与标准 PS 随机化流程不一致，协调者可控 `h` |
| ⑥ | **签名不绑定上下文**：不绑定集群、用途、时间 | `core.py:57-67` | 签名可跨集群 / 跨上下文重放 |
| ⑦ | **attestation 只是哈希且从未被验证**：协调者收集后原样回传 | `node.py:310-316`、`coordinator.py:155-158` | "证明"没有实际约束力，任何节点可伪造 |
| ⑧ | **`hash_to_G1` 实为 `hash_to_scalar × G1`** | `utils.py:45-56` | 偏离 RFC 9380；本项目场景可用，但不满足标准互通与证明要求 |
| ⑨ | **无 DKG 完成确认**：各节点对"DKG 是否成功"可能不一致 | `node.py:119-221` | 无一致性终态与广播 |
| ⑩ | **公开端点未鉴权**：`/health`、`/public_key` 无 `@require_token` | `node.py:254`、`326` | 信息泄露与探测便利 |

### 7.3 P2 — 工程与可靠性

- **无并发控制**：同一集群的并发签名请求无序号、无幂等键、无去重。
- **无重试 / 退避 / 熔断**：节点请求超时 10–15s 写死，失败仅 `print` 后继续；
  DKG 重试是固定 5 次 × 5s。
- **无速率限制**：任何人可高频调用 `/partial_sign` 做计算 DoS（配对运算极昂贵）。
- **无审计与可观测性**：没有结构化日志、请求追踪、指标、告警，只有 `print`。
- **无配置校验**：`NUM_MESSAGES` 在节点与协调者之间不一致时不会报错，只会静默失败。
- **无健康检查 / 就绪探针 / 优雅停机**：compose 中无 `healthcheck`，
  Docker 编排下 DKG 依赖"睡 3s + 轮询 60s"盲等（`node.py:368`、`339-360`）。
- **无协议版本协商**：节点与协调者之间没有版本字段，无法灰度升级。
- **密钥材料放在配置里**：`.env` 的明文测试值；`SHARE_PATH` 默认 `/data/...` 是容器路径（`node.py:39`）。

### 7.4 P2 — 性能（离生产可用差距最大的一项）

- **纯 Python 的 `py_ecc`**：BLS12-381 的配对与标量乘法在纯 Python 下**极慢**
  （单次配对通常为数十至数百毫秒量级），远慢于 `blst`/`mcl`/`arkworks` 等 C/Rust/汇编实现。
- **无批验证**：多个部分签名与多个签名的配对校验未使用随机线性组合批处理。
- **无缓存**：`Y_prod` 计算、配对预计算、公钥解析每次请求都重算（`core.py:84-91`）。
- **Flask 开发服务器**：不是生产 WSGI 服务器，无 worker 进程模型。
- **聚合是 O(n) 次标量乘 + 点加**，且每次签名都重新拉取并解析公钥。
- 结论：**当前实现只适合演示与正确性验证，不能承载真实并发。**

### 7.5 P3 — 测试与形式化（当前为空白）

- **没有任何测试文件**：仓库中没有 `tests/`、没有 pytest 用例。
  所谓"跑通"指的是**手动端到端演示成功**，不是可回归的自动化验证。
- 缺少：已知答案向量测试（KAT）、
  属性测试（正常签名必过 / 篡改必败 / 门限边界组合）、
  **恶意节点仿真**（重放、伪造份额、equivocation、重复 `party_id`）、
  失败注入（网络分区、超时、进程崩溃）。
- 没有性能基线与回归基线。
- 没有把实现对齐到论文的安全模型（PS 签名的不可伪造性归约、DKG 的保密性与健壮性定义）。

### 7.6 P3 — 标准化与互操作

- 自定义的未压缩点序列化（96B / 192B，`utils.py:61-141`）**不是任何标准编码**：
  没有压缩点、没有规范 DST、没有跨实现的 `hash_to_curve`。
- 因此**无法与任何真实 PS 实现或链上合约互通**，签名字节也无法被第三方独立验证。

## 9. 后续升级路线图

按优先级分四阶段。**第一阶段不做完，不要接触真实密钥。**

### 第一阶段：堵住密钥泄露（P0）

1. **移除 / 加固份额索取接口**
   - 把 DKG 份额传递改为**推送 + 一次性会话**：节点在 DKG 会话内**主动 POST** 份额给接收方，
     而不是暴露可被任意拉取的 GET。
   - 若必须保留拉取，则必须**校验请求方身份**（非对称签名 + 绑定目标节点 + 会话 nonce），
     并**在 DKG 结束后销毁该端点**。
2. **引入节点身份**：每个节点一对签名密钥，所有 DKG 消息签名；
   `AUTH_TOKEN` 从"共享口令"升级为"身份体系"（mTLS 或签名挑战）。
3. **`AUTH_TOKEN` 为空必须拒绝启动**，禁止"无 token 即放行"（`node.py:65`、`coordinator.py:73`）。
4. **全链路 mTLS**，杜绝份额与签名明文过网。
5. **统一门限语义**：配置改为显式 `(t, n)` 并在启动时校验 `t+1 <= n`，
   同时在日志与文档中打印"实际需要几个节点"。
6. **补齐输入校验**：`len(messages) == r`、元素类型检查、`party_id` 去重与参与集合校验。

### 第二阶段：让协议可被信任（P1）

7. 实现 **DKG 会话绑定**：session id、参与者集合承诺、每消息 nonce、防重放窗口。
8. 增加**投诉与排除**流程，并把"某节点作恶"变成**可验证证据**。
9. **公钥一致性确认**：DKG 结束后各节点交叉比对公钥摘要（或对摘要共同签名）。
10. 修复**重启导致密钥分叉**：份额缺失时**不得自动重跑 DKG**，
    必须进入"待恢复"状态并告警；引入密钥版本 / epoch，拒绝跨版本节点参与签名。
11. **密钥主动刷新**：定期（或按需）在不改变公钥的前提下重随机化份额。
12. 协调者不再无条件信任"第一个节点"，改为**多源获取公钥并交叉校验**（或门限获取）。
13. **独立随机化**：`h` 由参与节点各自贡献（可验证随机），而不是协调者单方决定。

### 第三阶段：工程化与性能（P2）

14. **替换密码学后端**：改用 `blst` / `mcl` / `arkworks` 等高性能实现（或其 Python 绑定）；
    引入**批验证**与配对预计算缓存。
15. **生产服务器**：gunicorn/uwsgi + 多 worker；节点间通信改为异步（aiohttp/httpx）。
16. **可观测性**：结构化日志（含 request id / cluster / epoch）、Prometheus 指标、分布式追踪、告警。
17. **可靠性**：超时 / 退避 / 熔断、幂等键、并发控制、速率限制、健康探针、优雅停机。
18. **配置治理**：统一配置源 + 启动时一致性校验 + 版本协商与灰度升级。
19. **审计**：不可篡改的签名审计日志（谁、何时、对什么消息、由哪些节点参与）。

### 第四阶段：可信度与标准化（P3）

20. **测试体系**：单元测试（含 KAT 向量）、DKG / 签名集成测试、**恶意节点仿真**、
    失败注入、模糊测试、性能基线；接入 CI。
21. **标准编码**：改用压缩点 + RFC 9380 的 `hash_to_curve`（含正确 DST），
    以便跨实现互操作与第三方独立验证。
22. **形式化与证明对齐**：把实现明确对应到论文的安全模型，
    记录所依赖的困难假设（如 PS 签名在相应假设下的不可伪造性）。
23. **引入 HSM / TEE**：份额的生成、持有与使用尽量不离开受保护边界。
